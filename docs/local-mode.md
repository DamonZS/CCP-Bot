# 本地模式：装完就能用的 CCP-Bot（不需要 Docker，也不需要 WSL 或虚拟机）

## 背景

CCP-Bot 桌面端一路走来都是「容器里的栈」：它自己挑一个容器引擎（Docker Desktop 或 Podman），把 compose 起起来，再把界面挂上去。这条路线有几个代价，而且都落在**第一次打开的人**身上：

- Windows 上 Podman 那一半要走 WSL，于是要么管理员权限，要么一台已经配好的机器；我们的桌面端此前甚至会直接拦一屏「This account cannot install Windows components」。
- Docker Desktop 那一半要先装 Docker、打开一次（第一屏是它的条款页），再等引擎预热。
- 两条路都要拉一堆镜像（GB 级），第一次「打开」到能用是十几分钟的量级。

而主人要的是 Claude / Codex / Cursor 那种体验：**装完双击就能用**。所以本地模式要做的事很直接——把这套栈作为**本机普通进程**跑起来，不碰容器、不碰虚拟机、不要管理员。

## 目标

- 引擎选择里增加「本地（本机进程）」并作为默认；选了它，Windows 的 WSL/管理员关卡**不出现**。
- 首次运行一次性准备好：便携版 PostgreSQL（下载一次、解包一次）、数据簇初始化一次、建库、写 `.env`、装依赖、构建界面、跑迁移、起 server 与 worker，等到 `/health` 通过，然后把界面挂上去。
- 之后每次启动复用数据簇与已装依赖，只做「起数据库 → 起进程 → 等健康」。
- 停止是干净的：端口不再监听，进程树里不留孤儿的 `postgres`。
- 每一步都有可读的进行中/失败说明；离线、端口被占、initdb 失败各有自己的句子，并且都指向下一步动作。
- 只绑回环地址：页面 `127.0.0.1:3010`，PostgreSQL 绑 `127.0.0.1` 上的空闲端口。

## 非目标

- 不改动容器路线：Docker / Podman 仍然可选，行为不变。
- 不在这一轮把**其余智能体进程**（agent-computer 的浏览器、agent-langgraph、supervisor、SPIRE）本机化——它们仍由容器路线提供。**内建 Bot（agent-bot）已经本机化**：它是纯 AG-UI 服务（只依赖 `bun` 与一个模型凭据），源码就在检出里，所以本地模式一并把它作为子进程起起来，服务端用 `MANAGED_AGENT_AG_UI_URL` 找到它。容器里的那批（浏览器、LangGraph、supervisor、SPIRE）仍需要引擎。
- 不做安装包签名。
- 不把 PostgreSQL 二进制塞进安装包（安装包体积会翻几倍）：首次运行下载一次，之后复用。

## 用户视角

1. 装好 CCP-Bot，双击。
2. 窗口里不再问 WSL 或 Docker，而是显示正在准备：CCP-Bot 源码（首次会下载一次） → 本机运行时 → 本地数据库（首次会下载一次） → 数据库扩展 → 数据库结构 → 内建 Bot → **它的「手」（computer：真正读写文件、跑命令的那个进程）** → 启动服务。
3. 十几秒到一两分钟后，窗口里就是 CCP-Bot 的界面，地址 `http://127.0.0.1:3010`。
4. 想让 Bot 在自己的项目里干活：把 `<检出>/workspace.txt` 写一行你的项目目录（或者直接删掉这一行，回到它自己的 `workspace/`）。界面上的「Hands on your files」那一行会写出它现在在哪个文件夹里干活。
5. 关掉再打开：跳过下载与初始化，只起进程。

## 功能要求

- **源码自己拿**：本地模式要有检出才能跑（`package.json`、`server/`、`app/`、`worker/`、`agent-bot/`）。一个从没这样装过的机器手上是**空文件夹**，而叫这个人「先去弄一份源码」正是这条路线要消灭的那种前置条件 —— 所以本地模式自己下载一次：复用容器路线同一条 `deployment::fetch`（发布版 tarball + 同一份 `unpack` 布局），版本从 `deployment_release::resolve_version` 取；失败会把「版本解析失败」与「下载失败」分开说清楚。下载这一步也算一个报出来的步骤（`checkout`）。**同时把 `agent-bot` 加进部署要复制的目录**：容器路线从镜像里拿 Bot、不读这份源码，但本地模式是从这棵树里把它当程序起起来的，漏掉它就等于「装完没有同事」。

- **引擎选择**：`local` 为默认；已保存过别的引擎的老机器不自动改（避免把正在用 Docker 的人的栈换掉）。
- **一次性准备**（首次运行）：
  - 便携 PostgreSQL：EDB 的官方二进制 zip，解包到 `<root>/postgres/pgsql`，**按 SHA-256 钉住**再解包——版本号是期望，digest 才是实际跑过的东西。按平台是一张表（同一份代码在 Windows 上也能断言 macOS 那一行）：

    | 平台 | 资产 | 大小 | SHA-256 | 解包后的目录形状 |
    | --- | --- | --- | --- | --- |
    | Windows x64 | `postgresql-17.6-1-windows-x64-binaries.zip` | 329,891,687 B | `d378882abd001a186735acd6f6ba716bca6ccd192e800412d4fd15ed25376b3e` | `pgsql/lib`、`pgsql/share/extension` |
    | macOS arm64 | `postgresql-17.6-1-osx-binaries.zip` | 358,923,135 B | `5afb85f5d764176bb00a527cfc5dd9127b9f8efaa33f5a9afbedbf6ceb985fcc` | `pgsql/lib/postgresql`、`pgsql/share/postgresql/extension` |

    macOS 那一包多一件事：里面有 119 个符号链接（`pgsql/lib` 下 35 个），按普通文件解出来是 19 字节的文本桩，而 `postgres` 要的是链接名——所以 unix 侧解包走 `zip` crate，逐条把链接重建出来（Windows 仍旧 `Expand-Archive`，那边没有链接）。macOS 包另有 741 MB 是 `pgAdmin 4.app`，本模式按路径段跳过、一个字节都不解。
  - **pgvector**：迁移文件的第一句就是 `CREATE EXTENSION IF NOT EXISTS vector;`，而 EDB 的便携版**不带**这个扩展（容器路线是从 `pgvector/pgvector` 镜像里拿到的）。所以还要下载一次很小的扩展包（同样按 SHA-256 钉住）：Windows 是 `vector.v0.8.6-pg17.zip`（169,689 B，来自 `andreiramani/pgvector_pgsql_windows`），macOS 是本项目自己构建并作为 release `pgvector-0.8.6` 发布的 `pgvector-macos-arm64.zip`（75,225 B，`1486659e0fd58bb4a253a69bc5c8dc3a03f806649cd8172e7ec06b3855d8fa16`）。放法与平台有关：库文件进 `pgsql/lib`（macOS 是 `pgsql/lib/postgresql`，文件名 `vector.dylib`），`vector.control` 与升级脚本进扩展目录（macOS 是 `pgsql/share/postgresql/extension`）。**两个包形状不一样**（Windows 嵌套 `lib/` + `share/extension/`，macOS 那三个文件就在顶层），所以放置按**文件名**找、不按目录形状；`vector.control` 在不在仍是「装没装」的判据。**少了它，第一次迁移就停在 `extension "vector" is not available`，后面全新的步骤一个都不会跑**——这是真机跑出来的，不是推测。
  - 数据簇：`initdb -U ccpbot -A trust -E UTF8`，落在 `<root>/postgres/data`；只监听回环，所以用 trust（不走网络就无所谓密码，也就没有第二份要保管的凭据）。
  - 建库：`createdb ccpbot`；库已存在算成功。
  - `.env`：**合并**写法——只覆盖我们要管的键（`DATABASE_URL` / `PORT` / `SERVER_PORT` / `APP_DIST_DIR` / `SINGLE_USER` / `NODE_ENV`），保留文件里其它键与注释。
  - 依赖与界面：`bun install`；`bun run --filter app build` 产出 `app/dist`（界面由 server 的 `serveStatic` + SPA 兜底提供，见 `server/src/app.ts:2016-2035`）。
  - 迁移：`bun run db:migrate`（在 `server/` 下跑，读 `../.env`）。
  - **内建 Bot**：检出里有 `agent-bot/src/index.ts` 就从**检出根**起一个 `bun --env-file=.env agent-bot/src/index.ts` 子进程（入口 import 的是 `../../shared/…`，所以工作目录必须是检出根），从 `<root>/bot/port` 取（或选一次）端口，只往它的环境里放 `PORT` 与 `MANAGED_AGENT_TOKEN` 两项（模型凭据由 `--env-file=.env` 读，与 server 读同一个文件），然后轮询它的 `/health`。服务端靠 `MANAGED_AGENT_AG_UI_URL` 认它 —— 这一项在 `.env` 里**始终被写一次**：有 Bot 就写地址，没有就写成空串（空串在服务端等于「没有」，见 `server/src/config.ts` 的 `optional()`，所以上一轮留下的地址不会骗服务端去注册一个不响应的 agent）。没有 Bot 的检出会明确说一声然后继续跑（界面与路由照常可用，只是没有可对话的同事）。
- **进程**：server、worker、内建 Bot 与 computer 各一个子进程，输出追加到 `<root>/logs/local-*.log`；Windows 上打 `CREATE_NO_WINDOW`，不弹控制台。macOS 上每个服务各起一个进程组，停的时候整组一起收——不然 bun 自己起的子进程会留下来占着端口（Windows 侧对应的是 `taskkill /T`）。
  - 健康：轮询 `GET http://127.0.0.1:3010/health` 直到 200。
- **让 Bot 真能干活（computer）**：会说话的 Bot 和会干活的 Bot 差一个 computer —— 文件与命令的工具都在它身上（`server/src/computer/*`）。所以本地模式也起它：`agent-computer/src/index.ts` 作为本机进程（工作目录是检出根），端口从 `<root>/computer/port` 取（或选一次），环境里给 `PORT`、`COMPUTER_TOKEN`（从 `vault` 铸出并记住）、`COMPUTER_BOT_ID=shared`、`PLAYWRIGHT_BROWSERS_PATH=<root>/computer/browsers`（**不占账号共享的 Playwright 缓存**：卸载 CCP-Bot 不该顺手带走别的东西的浏览器），以及 **`WORKSPACE_DIR` = 它被允许动的那个文件夹**。**刻意不给 `COMPUTER_PEOPLE_ONLY`**：那个标记属于「跑主人自己浏览器」的那条线（`local_browser.rs`），Bot 要的不是那一台。服务端靠 `.env` 里的 `AGENT_COMPUTER_URL`（有 computer 就写地址，没有写空串）与 `AGENT_COMPUTER_ALLOW_PRIVATE_HOSTS=true` 认它 —— 后者是必须的：本地模式的 computer 一定在私有地址（回环）上，compose 也是靠把 `NODE_ENV` 留空才让这条成立。
  - **工作文件夹**：默认 `<root>/workspace`；想指到自己的项目，就往 `<root>/workspace.txt` 写一行绝对路径（`set_workspace_folder` 写的也是它）。用文件而不是应用设置，是为了让「指哪儿」这件事可以靠改一行完成、撤销就是删掉那一行。安全性不在这一层而在计算机那一层：`agent-computer/src/workspace.ts` 把每条路径都限制在 `WORKSPACE_DIR` 里（绝对路径直接拒、解析后必须在根内、跟随符号链接后仍在根内），所以指到哪儿都关得住。
  - computer 的依赖**单独装**（`agent-computer/node_modules`）：它刻意不是 workspace 成员，根上的 `bun install` 从不碰它。
  - Bot 的依赖**也单独装**（`agent-bot/node_modules`）：`agent-bot` 同样不是 workspace 成员（根 `package.json` 的 workspaces 只有 app / server / worker / shared / toolkit / extension），所以根上的 `bun install` 从不装它声明的 `@ag-ui/core` / `@ag-ui/encoder` / `openai`。漏掉这一步的代价是干净安装上 Bot 立刻死：`logs/local-bot.log` 原文 `error: Cannot find module '@ag-ui/encoder' from <root>/agent-bot/src/index.ts`，`local_start` 就停在 bot 这一步、server 从不起来。开发检出看不出来，是因为它是 hoisted 布局、顶层碰巧有一份 `@ag-ui/encoder`——版本是 **1.0.2**，而 `agent-bot/package.json` 声明的是 **0.0.57**；部署用的 isolated 布局没有这份顶层副本，于是当场暴露。
- **复用**（第二次起）：数据簇已初始化就不再 `initdb`；`app/dist/index.html` 已在、依赖已在就不再装（有明确的「缺失才做」判据）。
- **停止**：先停 server/worker（进程树），再 `pg_ctl -m fast stop`；数据目录原地保留。
- **端口**：数据库端口选一次后写在 `<root>/postgres/port`，之后沿用（否则每次启动都会让 `.env` 里的连接串变化）；占用时换一个空闲端口。
- **错误**：下载失败（离线/被掐断）→ 说明可以重试、或改用容器路线；`initdb` 失败 → 把 `initdb` 的原始输出带出来；端口占用 → 换端口并说明。

## 首次运行只需要一个模型 key

除了一样，首次运行要的东西都由本机自己填掉：

- 便携 PostgreSQL、pgvector、数据簇、库：见上一节。
- **身份提供方**：`.env` 里写 `CCPBOT_SINGLE_USER=true`、`NODE_ENV` 留空，`server/src/auth/dev-actor.ts` 于是不再要求 `GOOGLE_OAUTH_*` 之类。
- **`KEY_ENCRYPTION_KEY`**：`server/src/config.ts:507` 的硬前置，由 `deployment_secrets()` 从 vault + `env::minted` 取得（与容器路线同一条判据，重启复用、不轮换），只放进子进程环境，不写 `.env`。
- **CopilotKit Intelligence 的三项**：`INTELLIGENCE_API_URL`、`INTELLIGENCE_GATEWAY_WS_URL` 与一个 key。`server/src/config.ts:1025-1050` 现在的判据是「三项**全缺**才是这台机器自己站着」：全缺时不拒绝启动，而是以 `mode: "sse"` 起，并在启动日志里留一行 `{"type":"intelligence-absent","mode":"sse","reason":"No CopilotKit Intelligence is configured, …"}`（记忆与会话留在本机自己的表里）；只缺其中一两项才是配错，照旧拒绝。所以本地模式**不再伪造连接**：`local.rs` 原来那份 `LOCAL_INTELLIGENCE` 占位值（`http://127.0.0.1:9/api`）与把它塞进 server 环境的 `server_environment()` 都已删除，server 子进程只拿到这份部署铸出的 secrets；人自己配了连接时照旧由向导写进 `.env`（`write_intelligence`），server 自己读那个文件——Bot 是回环上的内建进程，server 认的是 `MANAGED_AGENT_AG_UI_URL`。
- 于是留给人的只有**模型凭据**：`agent-bot` 没有它会直接退出（`OPENAI_API_KEY is not set, and no OPENAI_BASE_URL names an endpoint that needs no key`），而它决定 Bot 用哪个模型，所以本地模式不替人猜——向导的模型屏写它，或者自己在 `.env` 里写一行。本机路线的写法：窗口把模型屏的整个答案作为 `model` 交给 `local_start`（与容器路线同一个形状 `ChosenModel`），`start_stack_credential` 把它解析成凭据，`local::remember_model` 再用 `env::model_environment`（与 `env::compose` 共用的一条规则）算出这次答案拥有的键，并按 `vault::is_secret` 分流：**凭据**（`OPENAI_API_KEY` 这一类）进这台机器自己的凭据库 `<root>/.secrets`，**围绕它的设置**（`OPENAI_BASE_URL`、`BOT_MODEL`、`BOT_PROVIDER` 等）写进 `<root>/.env`；上一次答案拥有、这一次不再拥有的键从文件里取空，行尾不留旧值。子进程从环境里拿到凭据：`local::start` 把 `vault::recall_all(root, &env::MODEL_KEYS)` 并进那份 secrets，`hand_the_model_keys` 再把它转发给 bot / computer / worker——`--env-file` 不覆盖进程环境里已经设好的同名变量（bun 1.4.3 与 1.2.21 实测一致），所以凭据只能走环境。

两条边界（不是取舍，是「谁说了算」）：

- **没有连接就是没有连接**：本机路线一个 Intelligence 键都不写、也不放进子进程环境，server 因此走上面那条「三项全缺」的分支；`env::compose` 那边同理——向导没给连接时那四个键根本不进 compose 的 map（`insert_if_given` 的「空白不是值」，与模型键共用同一条规则），`.env` 里也不会留下四行空值装成一个半配好的连接。
- **人自己的连接永远赢**：`.env` 里有非空的 `INTELLIGENCE_API_KEY` 或 `CPK_INTELLIGENCE_API_KEY`（向导签到或粘贴 key 时写的就是它们）时，起来的就是那个连接，本机路线一个字都不动它（`write_env` 只写自己拥有的键、其余行原样保留）。

依据：`local::tests::live_start_serves_the_interface_on_this_machine` 现在**不写任何 Intelligence 配置**，也不自己往 `.env` 里写模型密钥：它把模型屏的答案（`ModelCredential::OpenAi { api_key: … }`）交给 `start()` 的 `model` 参数，整条栈照常起到 `/health` 200（见下方实测证据；它交出去的那把 key 落在 `<root>/.secrets`，不进 `.env`）；模型这条线由两条单测钉住：`a_model_choice_reaches_the_store_and_not_the_file`（key 在凭据库里、不在文件里，别人手写的那一行活着）、`a_run_with_nothing_to_answer_with_is_refused_before_it_starts`（空文件夹里既没有凭据也没有 keyless 端点就拒绝；凭据库里有 key、或文件里有非空的 `OPENAI_BASE_URL` 就放行）。Intelligence 那条线的判据现在是三条：`a_run_on_this_computer_writes_no_connection_of_its_own`（`write_env` 一个 Intelligence 键都不写；人自己写进去的连接，后续 `write_env` 也不动）、`env::tests::a_connection_nobody_configured_is_not_written_at_all`（容器路线：向导没给连接时那四个键不在 compose 的 map 里），加上这条 live 用例跑完现场看两件事——`<root>/.env` 里没有任何 `INTELLIGENCE_` 行、`logs/local-server.log` 里出现 `"intelligence-absent"`。

## 技术约束

- 只用既有依赖与外部程序：`bun`（既有的 `install::ensure_bun`）、`powershell`（解包 zip，与仓库既有的做法一致）、PostgreSQL 自带的 `initdb`/`pg_ctl`/`createdb`。**不新增 crate**。
- 所有命令都用绝对路径 + `CREATE_NO_WINDOW`，不经 shell 拼接。
- 日志只落在 `<root>/logs/`，不写系统目录。
- 不碰容器路线的文件与状态。

## 真机跑出来的坑（都已修，写在代码注释里）

1. **`pg_ctl start` 的管道会被 postmaster 继承** → 用 `.output()` 等它会在数据库已经起来之后仍然挂住（现场：测试进程 CPU 停住、日志显示 `database system is ready to accept connections`）。改成 `Stdio::null()` + `.status()`，失败原因改读 `<root>/logs/local-postgres.log` 的尾部。
2. **EDB 便携版不带 pgvector** → 第一次迁移停在 `extension "vector" is not available`（`Could not open extension control file … vector.control`）。Windows 接入 `andreiramani/pgvector_pgsql_windows` 的 `vector.v0.8.6-pg17.zip`（169,689 字节，SHA-256 钉住），只把库与扩展文件拷进去；macOS 那一份是本项目在 arm64 上构建、作为 release `pgvector-0.8.6` 发布的 `pgvector-macos-arm64.zip`（75,225 字节，SHA-256 钉住）——**不内置、不重编**：zip 带 mtime，重建就会改变 digest，把钉住的哈希变成摆设。两个包形状不同（Windows 嵌套目录、macOS 三个文件在顶层），所以放置改成了按文件名找。
3. **服务需要密钥才能启动（Intelligence 曾经也是前置）** → `KEY_ENCRYPTION_KEY must be configured`（`server/src/config.ts:507`）；密钥走 vault + `env::minted`（与容器路线同一条判据，重启复用不轮换）。Intelligence 三项**曾经**也是前置（旧文案 `CopilotKit Intelligence is required and is not configured. Missing: INTELLIGENCE_API_URL, INTELLIGENCE_GATEWAY_WS_URL`，`config.ts:1018`），服务端 `8611e30` 之后不再是：`server/src/config.ts:1025-1050` 把「三项全缺」当成本机自己站着的合法形状（`mode: "sse"` + 一行 `intelligence-absent`），本机路线因此一个占位键都不再伪造；只有人签到或粘贴过连接时才由向导写进 `.env`。
4. **server 必须从 `server/` 目录运行** → 从仓库根启动时租户包默认路径 `../examples/fintech` 解析到仓库外，直接 `ENOENT` 打不开 `brand.yaml`；现在两个服务都以 `server/` 为工作目录，server 读 `--env-file=../.env`、worker 以 `../worker/src/index.ts` 启动（与 compose 一致），worker 只拿它自己的三个变量。
5. **内建 Bot 要一个模型凭据** → 没有它，`agent-bot` 直接退出并说明 `OPENAI_API_KEY is not set, and no OPENAI_BASE_URL names an endpoint that needs no key`，从外面看只是「97 秒没有响应」。这正是向导里给模型密钥的那一步，本地模式不去猜、也不替人填：没有它就照实说 Bot 不响应。0.2.9 的真机复测还发现这一份答案**根本没到过 Bot**：`<root>/.env` 的 11 个键全是应用自己写的、`<root>/.secrets` 的六个 DPAPI 文件里也没有模型键（docs/install-verified.md §20.2），于是向导答完模型屏的人被告知「Bot 不能回答，因为没有模型」。现在答案从 `local_start` 的 `model` 字段一路传到 `local::remember_model`，按 `env::model_environment` 的同一份规则分流：凭据进这台机器自己的凭据库（`<root>/.secrets`），围绕它的设置进 `.env`，子进程从环境里拿到凭据（见坑 10）。
6. **部署要复制的目录里原本没有 `agent-bot`** → 空文件夹从发布版取源码时，Bot 会缺席（第一次跑这条 live 用例就断言失败在这里：清单在、`server/` 在、`agent-bot/src/index.ts` 不在）。它被补进 `deployment::ALSO_COPIED`，理由写在常量旁边：容器路线从镜像拿 Bot，本地路线从这棵树里起它。
7. **把检出改名（或搬走）会打断 workspace 软链** → `node_modules/@ccpbot/{shared,toolkit,recorder-extension}` 是 bun 建的工作区软链，指向创建时的绝对路径；目录改名后它们成了死链，症状是 server 起不来、日志最后一行 `error: Cannot find module '@ccpbot/shared/bot-prompt' from '<root>\server\src\index.ts'`（而界面那侧看起来只是「健康检查一直拒连」）。修法就是在新的路径下再 `bun install --frozen-lockfile --offline`（bun 重新建链，10 秒）。本条不是产品缺陷，但它把「搬动安装目录」变成一次需要重装依赖的操作，值得写下来。
8. **`agent-bot` 自己的依赖从来没被装过** → 根 `bun install` 只装 workspace 成员的依赖，而 `agent-bot` 不在 workspaces 里，所以它声明的三个包（`@ag-ui/core` 0.0.57、`@ag-ui/encoder` 0.0.57、`openai` ^4.104.0）在干净安装上一个都没有：0.2.7 的真机安装上 Bot 起手就 `error: Cannot find module '@ag-ui/encoder' from <root>/agent-bot/src/index.ts`（`Bun v1.4.3 (Windows x64)`），`local_start` 停在 bot 步骤、server 从不起来、界面停在连接屏。开发检出一直没露出来，是因为它是 hoisted 布局、顶层碰巧有一份 `@ag-ui/encoder`，而那份是 **1.0.2**、不是声明的 0.0.57——能解析，所以也没人发现一直在用错版本；部署的 isolated 布局每个 workspace 有各自的 `node_modules`、没有顶层副本，于是当场暴露。修法与 computer 对称：`<root>/agent-bot` 自己 `bun install` 一步，判据是 `<root>/agent-bot/node_modules` 在不在。
9. **`<root>` 还不存在时，第一次 Start 6 秒就失败**（0.2.9 真机）→ 界面 `That did not finish` / `Could not remember the local choice.`，细节原文 `writing C:\Users\Damon\CCP-Bot\.ccpbot-local failed: 系统找不到指定的路径。 (os error 3)`。`main.rs` 在部署下载（`deployment.rs` 的 `create_dir_all`）之前就调 `local::remember`，而它只是一次 `std::fs::write`；修法是让 `remember` 自己先备好前置条件（`create_dir_all(root)` 再写标记，注释里写明实测的 os error 3），判据由单测钉住：不存在的目录会被建出来、标记写成功、`wanted()` 为真，根安装不是 Bot 的安装那条也是单测。
10. **凭据进凭据库、设置进 `.env`；没有答案的启动当场被拒** → Bot 由 `--env-file=.env` 启动，而 `--env-file` **不覆盖**进程环境里已有的同名变量（bun 1.4.3 与 1.2.21 实测一致），所以本机路线把 `env::model_environment` 算出的那份答案按 `vault::is_secret` 分流：凭据（`OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN` / `CHATGPT_OAUTH_TOKEN`，以及兼容端点那把 key）进 `<root>/.secrets`（DPAPI），设置（`OPENAI_BASE_URL`、`BOT_MODEL`、`AGENT_BOT_MODEL`、`BOT_PROVIDER`、`CCPBOT_MODEL_OAUTH_FILE`、`CHATGPT_AUTH_FILE`）写进 `<root>/.env`，上一次答案的残值从文件里取空——这两件事一次做完（`vault::write_env_after_remembering`）。`local::start` 随后把 `vault::recall_all(root, &env::MODEL_KEYS)` 并进那份 secrets，`hand_the_model_keys` 把它转发进 bot / computer / worker 的子进程环境；容器路线一个字都没变（`env::compose` 仍走 `env::model_environment`，输出逐字节相同）。判据（单测）：`a_model_choice_reaches_the_store_and_not_the_file`（key 在凭据库里、不在文件里，别人手写的行活着）、`a_run_with_nothing_to_answer_with_is_refused_before_it_starts`（空文件夹既没有凭据也没有 keyless 端点就拒绝；凭据库里有 key、或文件里有非空 `OPENAI_BASE_URL` 就放行）。拒绝发生在 `local_start` 调 `local::start` 之前，所以是一秒内的事，而不是下载完运行时再在 Bot 步骤失败。请求里没有答案、而凭据库里还留着上一次那份时，旧 key 会经进程环境生效（`--env-file` 不覆盖进程变量）——这正是「第二次 Start 不再问」的代价，换 key 走模型屏、或先删掉 `<root>/.secrets\OPENAI_API_KEY.dpapi`。真机 live 实测（`cargo test --lib -- local::tests::live_start_serves_the_interface_on_this_machine --include-ignored --nocapture`）：**先把凭据库里的 `OPENAI_API_KEY` 删掉、再把 `<root>/.env` 里 11 个模型键整行删掉**（`Select-String` 确认为空），仍走完整步骤链 `[bot] The built-in Bot is answering (/health 200).` → `[ready] CCP-Bot is running on this computer (/health 200).`，`test result: ok. 1 passed; 0 failed; 0 ignored; 658 filtered out; finished in 13.78s`（只删凭据库那一轮 17.24s）；跑完 `<root>/.secrets\OPENAI_API_KEY.dpapi` 352 B、时间戳就是这一轮，而 `<root>/.env` 里始终没有 `OPENAI_API_KEY`（只有 5 行空值设置）。也就是说那把 key 只可能来自请求里的答案。`logs/local-bot.log` 尾行 `agent-bot listening on http://127.0.0.1:63659/ag-ui`，跑完 `<root>/.env` 的哈希与跑前逐字节相同。
11. **重开的窗口不认本机栈是自己的，Stop 去问 Compose**（0.4.0 之前的真机）→ 本机栈起着、`/health` 200 时窗口报 `CCP-Bot could not verify its app on port 3010 belongs to this installation. Try starting CCP-Bot again.`，按 Stop 报 `Compose down failed: CCP-Bot has no runtime ownership for this installation.`：所有权只认 Compose 引擎留下的记录，本机路线什么都没写。修法是把这一次运行起的四个进程按身份记下来：`local_start` 在子进程进了 `shell.local_children` 之后写 `<root>/.logs/host-pids.json`（`stack::record_host_processes`，v1 Records：server / worker / bot / computer 各自的 pid、可执行文件、命令行与创建时间），写不进就把刚起的栈停掉再报错；`local_stop` 停完栈立刻 `stack::forget_host_processes` 把这份记录删掉。读端只认「身份还对得上」的进程：`recorded_process_owns_port` 要求该端口上**每一个** listener 都在记录里（按进程实例与父子链验证，而不是「端口上有人答就算」），而本机根问 `app` 就等于问记录里的 `server`——机器上没有单独的 app 进程，接口就是 server 那个进程，`recordable_host` 也因此把 `bot` / `computer` 一起列进可记录的名字。`already_running_on` 同时认本机根：没有容器 stamp 的时候，标记（`local::wanted`）加上这份记录就是「这个安装起了它」的证据；一正一反由单测钉住——`a_folder_this_computer_runs_is_running_only_when_its_own_record_proves_it` 与既有的 `already_running_returns_false_when_ownership_is_unproven`。真机 live 实测（`cargo test -p ccpbot-desktop --manifest-path desktop/src-tauri/Cargo.toml --bin ccpbot-desktop -- tests::live_a_run_on_this_computer_records_what_it_owns --include-ignored --nocapture`）：整链到 `[ready] CCP-Bot is running on this computer (/health 200)`，随后问 app 为真、`already_running_on` 为真；`local::stop` 之后记录已删、再问 app 为假，`test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 117 filtered out; finished in 18.45s`。

12. **关窗口只是把窗口藏起来，退出才停栈** → 这是个托盘应用：`WindowEvent::CloseRequested` 只 `prevent_close()` + `window.hide()`（`main.rs:4795`），点右上角的关闭**不会**停掉本机栈；真正停栈的是菜单 Quit（`RunEvent::ExitRequested` → `exit_cleanup_with`：先按记录停进程 → 容器那条对本机根直接跳过 → `local::stop` 收子进程与本机 postgres，注释写着「Quitting 是另一种『停』的说法，本机数据库也得跟着走——没有别人知道这个进程起过数据库」）。0.2.9 的真机现场是**强杀窗口进程**：4 秒后仍能看到 bun×4、postgres×30、3010 还在监听——强杀不经过任何清理，这一点本模式改不掉；能改的是留下的痕迹够不够让下一次启动认出来：标记与 `<root>/.logs/host-pids.json` 都还在，所以下一次 Start / Stop 仍能按身份停掉那批进程，而清理没做完的失败会写成退出清理通知（`QuitCleanupNotice` → `<root>/quit-cleanup.json`），下一次启动看得到（`recovery_required_or_pending_quit_notice`）。判据：离线用例 `quitting_stops_the_processes_a_run_on_this_computer_started`（本机根的文件夹 + 一个真在跑的进程 → 走退出清理 → 进程真的没了、`shell.local_children` 清空、且没有任何 `Compose down failed`，也就是没去问 Compose）与 `a_local_stop_failure_of_the_quit_cleanup_reaches_the_next_start`（本机那条失败落成 `host-processes` 类通知、下一次启动能看到）；真机 live 用例 `live_quitting_stops_the_stack_this_computer_started`（真栈起来 → 走同一条退出路径）：整链到 `[ready] CCP-Bot is running on this computer (/health 200)`，走完退出清理后 `test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 120 filtered out; finished in 20.68s`，跑完 3010 一个监听都没有、这个项目的 postgres 与 bun 进程全没了、`<root>/.logs/host-pids.json` 已删、标记也恢复原样。强杀那条由 installer-verify 在出厂包上复测。

13. **`agent-computer` 要一个可写的浏览器 profiles 目录，本机路线从没告诉过它** → 它自己的 fallback 是 `/profiles`（`agent-computer/src/index.ts:276-299`：`mkdir` 加写探针，不成就 `console.error` 之后 `process.exit(1)`）。macOS 的根是只读的，于是第一次在 Apple silicon runner 上跑就落地为 `The browser profiles directory at /profiles is not writable by uid 501: Error: EROFS: read-only file system, mkdir '/profiles'`，computer 启动即退，从外面看只是「端口无人应答」（`Connection refused`）。Windows 是**侥幸**：同一段 fallback 能建出 `C:\profiles`（实测它存在，`CreationTime 2026/10/31 21:05:38`，机器上只有这段代码会造它），所以这个漏项在本机路线上藏了很久、直到 mac 才暴露——**不是 mac 特有 bug，是本机路线漏了一项**。另外三条路线本来就给这个键：`stack.rs`（`PROFILES_DIR={data}/profiles`）、`local_browser.rs`、`charts/ccpbot/templates/computer/statefulset.yaml:131`。修法：`local::profiles_folder(root)`（`<root>/computer/profiles`）由 `computer_environment` 作为 `PROFILES_DIR` 交给 computer，**三个平台一视同仁**（Windows 也不再往 `C:\profiles` 写）。判据：单测 `the_computer_is_told_which_folder_to_work_in`（键在、落在 `<root>` 下、不等于 `PLAYWRIGHT_BROWSERS_PATH`）；接线另有一条实测——把这个环境交给 computer 单独启动时 `PROFILES_DIR=<root>\computer\profiles` 被建出来、`/health` 200、kill 后端口归零（那条只验接线，不是整栈）。

14. **一个服务起不来时，它的日志要跟着失败一起走** → 上面那条的发现过程本身证明了这条纪律：computer 在 mac runner 上退出，测试只说 `The computer did not answer.`（`http://127.0.0.1:49452 never answered /health. Last time: Connection refused (os error 61)`），而原因写在 runner 的 `logs/local-computer.log` 里，**runner 一删就没了**——那次不得不改工作流、重跑一遍才能读到那一行。现在 computer 等不到 `/health` 时，那条 `Problem` 的 detail 会把它自己那份日志的尾部（80 行以内，`tail_of` 读）附在后面：主句一字不动、超时值不动、只多一份证据。同一份判据也给了 live 用例：`local::logs_on_failure(root)` 把 `<root>/logs/local-{server,bot,computer,postgres}.log` 各取尾部 40 行拼成一块，用例在 `start()` 失败时把这块接在 `the local stack should start: …` 后面（断言本身不动、正常路径的输出逐字不变）。用途正是「没法回头看的机器上，失败要自己带着原因」。

15. **新部署下载的是「这一版自己的发布」，不是 latest** → 之前本机路线（连它自己的两条 live 用例）靠匿名调 `https://api.github.com/repos/DamonZS/CCP-Bot/releases/latest` 决定下哪一份源码，两个后果都在真机上出现过：mac runner 共享的出口 IP 被匿名限流，报 `could not find the latest CCP-Bot release: … answered 403 Forbidden`（与那台 Mac 本身毫无关系）；更要紧的是**版本错位**——用例拿已发布版（0.3.2）的源码、用本树 0.4.0 的路线去起它，而 0.3.2 的服务端仍硬要求 CopilotKit，于是服务拒绝启动，从外面看只是 `CCP-Bot started but its interface never passed the health check. / Connection refused (os error 61)`。现在 `deployment_release` 先取**构建自己的版本**（编译期嵌进根 `package.json` 的 `version`，tag 即 `v<version>`），只有这一版自己的发布确实不存在（404）时才回退 latest；403/限流/离线是**另一种答案**，原文照报、绝不被当成「这一版没有发布」（读状态码的地方只有 `no_such_release` 一处）。两条 live 用例因此有了可复核的跳过语义：本版还没发布时打一行点名，例如 `live_an_empty_folder_is_filled_from_the_release: skipped, v0.4.0 is not published yet`，并断言自己什么都没下载；`CCPBOT_LIVE_RELEASE=v0.4.0` 可以点名一个版本，发布之后就点名跑，而不是每次都问「最新是什么」。

16. **不要为了「问一句」而起一个进程；起了的进程就要等到、等不到就杀掉** → 0.4.0 出厂包的裸装复验（`docs/install-verified.md` §50）里有两件事：启动过程中弹了两个 `pg_ctl.exe - 应用程序错误` 硬错误框（`class=#32770`、owner `csrss`），停机后 4 个 `pg_ctl.exe` 残留（同一轮 `postgres` 自己是 0）。诊断的结论是：**前者不是「pg_ctl 崩了」**——那段时间（04:55–05:10）Application 日志里的崩溃都是别的进程（豆包输入法 `ImeService.exe` 3 次：`0xc0000374` / `0xc0000409` / `0xc0000005`，还有 installer-verify 的 `powershell.exe` 在 `wmidcom.dll` 里 `0xc0000005`），按 `pg_ctl` 过滤近三天一条都没有；`#32770` 的 owner 是 csrss 意味着走的是**加载器/硬错误**那条路（`NtRaiseHardError`，不写 Application 日志），也就是某个 `pg_ctl` 调用**没能正常退出**，而我们的代码在它旁边既没有等待预算、也没有杀它的路径。数量从哪来：窗口每秒问一次 `local_status`（`desktop/src/App.tsx:682` 的 `setInterval(…, 1000)`），`local_status` 里的 `database_running` 调 `local::postgres_running`，而当时的实现是 `pg_ctl -D <data> status` 加 `.output()`——**一次轮询一个进程**，第一趟六分钟就是几百个；其中卡住的那个，读它的线程永远不返回。现场实测（写这份文档时，机器上装着 0.4.x 的 `C:\Users\Damon\CCP-Bot`）：两个 `pg_ctl … status`（pid 24272 / 28548，parent 9540）从 06:01 一直活到 06:16 还在，而它们那个 3010 上连监听都没有。修法两半，同一条规则（起了的进程是自己的责任）：`postgres_running` **不再起进程**——读 postmaster 自己的 `postgres/data/postmaster.pid`，再探它被指定的那个端口，两件事实、零进程（`a_running_database_is_answered_by_the_machine_without_a_helper` 用一个**根本没有 `pg_ctl` 的 root** 钉住这一点）；`start` / `stop` 仍然必须调 `pg_ctl`（起停数据库只有它会做），但等它要有预算——start 是 `pg_ctl` 自己的 `-t 90` 再加 20 秒，stop 是 30 秒——超时就**杀掉它**，然后问机器实际发生了什么（数据库起来了就算起来了、还答着就算没停），而不是信 helper 的话（`a_helper_that_never_comes_back_is_killed` 用一个真在跑的进程钉住「会被杀、会被回收」）。同一次实测的对照：改动后跑同一条本机栈 live，**自己起的 `pg_ctl` 只有两条**——`… -o "-p 63133 -h 127.0.0.1" -w -t 90 start`（06:15:08）与 `… -m fast -w stop`（06:15:41），退出后 0 个残留，而 `status` 那一条不再出现。停机后 4 秒与 30 秒两个时间点（3010 监听 / 本项目 postgres / 本项目 bun）都是 0。

17. **匿名问 GitHub 有 60 次/小时/地址的上限；共享出口 IP 上会拿到 `403 Forbidden`** → GitHub 对匿名请求按**地址**计数（60/小时），而这个地址不是「这台机器」的：CI runner、办公室 NAT、手机热点后面的人都算同一个地址。别人把这 60 次用完，本机路线第一次运行去问「我这一版发布了吗」就会拿到 `403 Forbidden`（真机实测：`local-mode-macos` 的 run `41244677722` 上那两条「取发布版」的用例被点名跳过；同一条 URL 在本机匿名请求是 `HTTP/1.1 200 OK`，响应头 `X-RateLimit-Limit: 60` / `Remaining: 59`）。应用**如实报错、不会偷偷回退到最新版**——回退会把另一个版本的源码解出来，正是 0.4.0 修掉的那种错位；`403` 与「这一版确实没有发布」是两种答案，读状态码的地方只有 `no_such_release` 一处，它只认 404。解法：设 `CCPBOT_RELEASE_TOKEN`、`GH_TOKEN`、`GITHUB_TOKEN` 三者之一（按这个顺序取第一个非空值），请求会带上 `Authorization: Bearer <token>`，限制就抬到账号级；**这个 token 只进请求头**——不进 `.env`（那份文件要交给 Bot 与 Compose）、不进日志、不进任何 `Problem` 的文本，而且只发给 GitHub 自己的域名（同一个下载 helper 还要去 `get.enterprisedb.com` 取便携数据库，token 不会跟着去第三方）。三个都没设时与今天逐字相同：匿名请求，不新增任何必填项。判据是四条单测：`the_names_are_tried_in_order_and_a_blank_one_is_not_a_token`、`the_token_goes_to_githubs_own_hosts_and_nowhere_else`、`a_request_that_may_carry_the_token_carries_it`、`a_request_for_somebody_else_carries_none_and_nothing_set_is_anonymous`。
